## Slide 2: 研究主线一：信任不是行政命令的产物

**核心问题**
- 开源组织可以“创建”吗？
- 生态可以“规划”吗？
- 信任能被采购、考核、动员吗？

**研究判断**
- 生态是结果，不是手段
- 能“构建”出来的通常不是生态，而是动员体系
- 开源的核心问题是制度设计：产权、交易成本、声誉、退出、贡献归属

**参考框架**
- 科斯：交易成本决定组织边界
- 威廉姆森：L1→L4 制度层次
- 奥斯特罗姆：自组织与公共池塘资源
- 阿西莫格鲁：包容性 vs 汲取性制度
- 卢曼：信任是降低复杂性的社会机制

---

## Slide 3: 研究主线二：大分流 2.0

**核心问题**
- 为什么开源在西方形成了制度化协作网络？
- 为什么在中国常常表现为工具化、项目化、活动化？

**工作框架**
- 真开源：FLOSS / 公地型开源 / 上游优先
- 伪开源：特许工程代码 / 局域网共享 / 赛博庄园 / 活动型开源
- 开源在中国不是靠市场存活，而是常常被转移到教育系统、产业联盟、行政动员或企业内部流程中存活

**研究边界**
- 这是观察框架，不是定性裁决
- 用于解释现象，不用于替代组织判断

---

## Slide 4: 研究主线三：本地化开源基础设施链

**观察对象**
- 代码托管
- 包镜像与分发
- 合规审计
- 开发者工具
- 社区与活动平台

**研究问题**
- 每一层由谁提供？
- 谁是商业方、教育方、行政方、社群方？
- 提供者的激励是否与贡献者权利一致？
- 本地化链路是降低了协作成本，还是增加了治理复杂度？

**与 OSPO 的关联**
- OSPO 可以成为“上游优先”的组织接口
- 也可以成为本地化采购与合规控制的接口
- 两者不同，需要在内部机制上区分

---

## Slide 5: 研究主线四：真实世界的需求与消费

**核心问题**
- 开源项目的需求来自哪里？
- 谁消费 issue、PR、release、文档、社区讨论？
- 贡献者为什么留下？

**研究对象**
- GitHub issues
- PR review
- release notes
- 用户场景
- maintainer 行为
- 贡献者金字塔

**研究视角**
- release 不是 changelog，而是需求信号
- issue 不是抱怨列表，而是消费者侧的集体制图
- PR 不是提交记录，而是贡献制度如何分配收益和成本的证据

## Slide 6: 研究主线五：Agent 时代的开源制度

**研究对象**
- Hermes Agent
- Claude Code
- Codex
- Continue
- MCP
- 多 agent 协作

**核心问题**
- Agent 是工具，还是新型参与者？
- 谁来负责 agent 的行动？
- license、memory、skill、MCP、subagent 如何构成新的协作边界？
- 真实世界的需求如何推动 agent 开源项目的架构演化？

**研究假设**
- Agent 正在从“命令执行器”变成“制度参与者”
- 开源项目会因此重新设计信任、审批、记忆、审计、贡献和退出机制

## Slide 8: 我希望与京东 OSPO 交换的问题

**问题一：上游优先**
- 哪些项目在“先上游贡献，再内部使用”？
- 哪些项目是“内部跑通，再选择性开源”？
- 这两条路径在组织内部如何被识别？

**问题二：贡献归属**
- 京东员工的开源贡献，是个人行为、商业贡献，还是组织责任？
- 谁批准外部提交？谁负责 license 判断？谁维护长期关系？

**问题三：生态边界**
- 京东参与的是全球开源生态，还是本地化开源生态？
- OSPO 是社区桥梁，还是合规/采购/营销接口？

**问题四：AI Agent**
- 当 agent 参与开发、评论、审批、维护时，京东希望如何承担责任？
- 哪些动作必须人类批准，哪些可以由 agent 建议？

## Slide 9: 结语

**一句总结**
- 「开源之道」关心的不是“有没有做开源”，而是“开源以何种制度运行”。

**可带走的研究方向**
- 信任不能行政制造
- 生态是结果，不是手段
- release、issue、PR 是真实需求的现场
- Agent 正在成为新的制度参与者
